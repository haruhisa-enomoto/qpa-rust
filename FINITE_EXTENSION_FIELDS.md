# Finite extension field campaign

Last updated: 2026-07-22

Status: complete

## Objective

Add one exact, runtime-configured implementation of `GF(p^n)` for prime `p`
and positive `n`. This is a coefficient campaign for the source-faithful QPA
port: it must make the existing Rust and Python QPA computations work over
finite extension fields without replacing QPA, GBNP, or transitive GAP
algorithms with independently selected algebra algorithms.

`GF(4)` is an acceptance case, not a special implementation. The same field
type and public construction path must cover `GF(8)`, `GF(9)`, `GF(16)`,
`GF(25)`, and every other field for which the construction data and resource
limits are satisfied.

## Design decisions

- Keep Numerica as the exact `Ring`/`Field` contract used by the generic QPA
  implementation.
- Implement a local `GaloisField` and `GaloisFieldElement` in `qpa-core`.
- Use a coefficient-vector representation in
  `F_p[x] / (f(x))` as the correctness-first reference representation.
- Use GAP's Conway polynomial and designated primitive element conventions for
  canonical construction, display, enumeration, and compatible subfields.
- Admit explicit irreducible moduli as a separate construction path, but never
  describe an arbitrary-modulus field as GAP-canonical.
- Keep field construction and arithmetic deterministic. Optimized Zech-log
  storage may be added only behind the same observable contract.
- Keep external finite-field libraries optional. A later accelerator must pass
  the same GAP oracle suite and must not leak through the public QPA API.

## Performance policy

Correct polynomial-basis arithmetic is the reference path. Benchmark before
adding Zech tables, packed characteristic-two vectors, Karatsuba multiplication,
or an external backend. Enumeration-heavy QPA operations may impose explicit
limits based on `q` and the surrounding vector-space dimension; those limits
do not narrow the set of finite fields representable by the scalar layer.

## Completion definition

This campaign is complete only when the generic `GF(p^n)` construction is
public in Rust and Python, all currently supported QPA API families work over
it whenever their pinned QPA methods admit finite fields, all extension-field
branches have source mappings, and the complete verification matrix above is
green. Passing a GF(4)-only example is not completion.

## Source map

The implementation is tied to the frozen revisions in
`porting/upstream-lock.toml`:

- GAP `lib/polyconw.gi`, especially `ConwayPol` and `ConwayPolynomial`, defines
  validation, base-`p` decoding, candidate order, primitivity, compatibility,
  and the on-demand fallback used by `qpa-core::finite_field`.
- GAP `lib/conwdat1.g`, `conwdat2.g`, and `conwdat3.g` generate
  `crates/qpa-core/src/conway_table.tsv` through
  `scripts/generate-conway-table.py`. GAP `src/finfield_conway.h` supplies the
  small kernel table retained as a fast path.
- QPA `lib/algebra.gi:14-45` defines `PowerSubalgebraOp`; its `p^n` exponent is
  represented by `QpaCoefficientField::qpa_degree_over_prime_field` and the
  corrected structure-constant implementation.
- GAP `lib/algmat.gi:867-987` defines the positive-characteristic
  `RadicalOfAlgebra` branch and its inverse Frobenius progression.
- GAP `lib/polyfinf.gi` defines the finite-field factorization stages used by
  QPA's primitive-idempotent/decomposition call graph; the Rust translation
  now uses `q = p^n` for distinct-degree and common-degree factorization and
  inverse Frobenius for inseparable roots.
- QPA module, homological, and endomorphism-quiver methods remain the source of
  those generic algorithms. This campaign changes their coefficient contract
  and restores their finite-extension dispatch; it does not replace them.

The scalar representation can construct any `GF(p^n)` whose exact integers and
polynomial computation fit process resources. Operations which enumerate the
whole field additionally require `p^n` to fit Rust address space and available
memory; they return a typed error otherwise. The checked-in Conway database is
a speed and reproducibility layer, not a finite whitelist: missing rows invoke
GAP's deterministic `ConwayPol` procedure.
